# 预警中心与自动化处理设计

## 目标

在 GatewayOps 中增加统一的预警中心，把现有消息通知纳入预警流程，支持针对中转站账号和中转站用户的规则、自动化处理、自动恢复与通知。

本设计覆盖以下能力：

- 账号类预警：倍率变化、渠道余额、账号消耗、稳定性；
- 用户类预警：用户消耗、多 IP；
- 自动停排、自动恢复调度、自动停用用户、自动启用用户；
- 可配置恢复条件或明确关闭自动恢复；
- 规则选择现有通知渠道，发送内置格式的消息；
- 复用 sub2api 现有数据，同时为 newapi 留出适配能力；
- 使用定时采集和本地规则评估，不把预警逻辑放进中转请求热路径。

## 对象边界

账号类规则只针对中转站同步的上游账号，即 `RelayAccount`。用户类规则针对中转站用户，使用中转站返回的稳定用户 ID；现有数据只有邮箱时，邮箱作为兼容性的后备标识。

`ChannelAccount` 不作为独立预警对象。它是 GatewayOps 登录渠道站点、采集余额和倍率的账号，作为 `RelayAccount` 的数据来源。账号与渠道账号之间通过现有的中转站账号关联关系解析。

对于一个中转站账号关联多个渠道账号的情况，余额规则使用所有关联渠道账号中最新且未过期的最低余额，避免其中一个上游凭据余额不足时继续调度。没有有效关联或所有余额数据过期时，规则进入 `unknown`，不会直接判定为余额异常。

自动化动作的作用域固定为中转站：

- `RelayAccount` 只能执行停止调度和恢复调度；
- 中转站用户只能执行停用和启用；
- `ChannelAccount` 不执行停排或启停动作。

## 方案选择

采用“定时采集 + 本地规则评估 + 持久化状态”的方案。

1. **定时采集与规则评估，推荐**：复用现有 scheduler、monitor、relay usage 和渠道快照，预警服务读取本地数据并维护事件状态。行为稳定、不会增加中转请求延迟，sub2api 与 newapi 可以共用规则引擎。
2. **请求实时事件驱动**：在每次请求完成时计算消耗、IP 和稳定性。实时性更高，但会把失败和统计逻辑放入请求链路，也会让不同中转站的事件口径难以统一。
3. **混合模式**：请求事件处理消耗和 IP，定时任务处理余额、倍率和稳定性。实时性最好，但需要额外事件总线、幂等和两套状态合并逻辑，第一版维护成本过高。

## 采集与评估频率

采集频率与规则评估频率分开。规则评估只读取本地数据，不在每轮评估中重复请求上游。

| 数据 | 默认频率 | 可配置范围 | 说明 |
| --- | ---: | ---: | --- |
| 规则评估 | 1 分钟 | 固定为 1 分钟 | 更新状态、事件、动作和通知 |
| 账号倍率 | 1 分钟 | 30 秒～15 分钟 | 比较最近两次有效倍率 |
| 账号稳定性 | 1 分钟 | 30 秒～5 分钟 | 从请求记录计算错误率与延迟 |
| 账号和用户消耗 | 1 分钟 | 1～5 分钟 | 计算滑动窗口和基线 |
| 用户 IP | 1 分钟 | 1～5 分钟 | 计算窗口内去重 IP |
| 渠道余额 | 5 分钟 | 1～30 分钟 | 读取关联渠道账号余额 |

采集任务先判断现有快照是否满足新鲜度要求。已有任务产生的数据足够新时直接复用；不足时由预警采集任务补充。这样不会因为新增预警功能重复请求同一个上游接口。

系统设置增加预警采集开关和上述频率配置。频率下限由后端校验，避免误配置造成对上游接口的高频压力。

## 规则通用模型

每条规则保存以下信息：

- 名称、启用状态、严重级别；
- 目标类型：`relay_account` 或 `relay_user`；
- 目标范围：全部中转站、指定中转站、指定账号或指定用户；
- 指标类型；
- 条件配置；
- 统计时间窗口；
- 最少样本数或最少请求数；
- 连续触发次数；
- 连续恢复次数；
- 通知冷却时间；
- 自动化动作配置；
- 自动恢复配置；
- 绑定的通知渠道；
- 创建、更新时间和最近评估时间。

规则的稳定字段用于列表筛选和索引，指标差异较大的条件、动作和恢复配置使用版本化 JSON 保存。规则读取时按 `kind` 校验 JSON 结构，未知字段保留但不执行，便于后续增加 newapi 能力。

所有规则默认使用 1 分钟评估周期。规则不单独配置采集周期，避免同一个数据源被多条规则重复拉取；规则只配置自己的窗口、阈值和连续次数。

## 规则定义

### 倍率变化

目标为 `RelayAccount`，比较当前倍率与上一次有效倍率。

- 支持相对变化阈值，例如绝对变化达到 20%；
- 支持绝对变化值阈值；
- 第一次有效采集只建立基线，不触发预警；
- 旧值缺失、旧值为 0、采集时间过期时进入 `unknown`；
- 倍率规则使用账号维度，不把同一账号的多个分组变化重复生成多条事件。

### 渠道余额

目标仍为 `RelayAccount`，数据来自关联的 `ChannelAccount`。

- 支持余额小于或小于等于固定金额；
- 支持连续低于阈值的次数；
- 多个关联渠道账号取最低有效余额；
- 余额采集失败或过期时进入 `unknown`；
- 恢复条件默认是余额连续达到恢复阈值，恢复阈值可以高于触发阈值形成滞回，避免余额在边界附近反复触发。

### 账号消耗异常

目标为 `RelayAccount`，数据来自中转站用量事件。

支持两种模式：

1. **固定阈值**：指定窗口内的消耗金额达到阈值，例如 15 分钟消耗不少于 30 美元。
2. **基线比较**：当前窗口消耗同时满足“超过过去基线倍数”和“超过最小金额”两个条件，例如超过过去 7 天同窗口平均值的 3 倍且不少于 10 美元。

两种模式均支持最少请求数、连续窗口数和通知冷却时间。窗口采用滑动窗口，评估时以当前时间向前计算，不依赖自然小时或自然日边界。

### 稳定性异常

目标为 `RelayAccount`，每条规则选择一个稳定性指标：

- 请求错误率；
- 首 Token 延迟 P95；
- 总响应耗时 P95；
- 连续失败次数。

规则必须配置最少请求数，低于最少请求数时进入 `unknown` 或保持上一状态，默认不产生异常。延迟指标只使用存在有效延迟数据的请求，不能把缺失延迟当成零。

### 用户消耗异常

目标为 `RelayUser`，计算逻辑与账号消耗异常一致，聚合键改为中转站 + 用户外部 ID。

用户外部 ID、邮箱和展示名称作为事件上下文保存，用户邮箱变化不会导致同一用户生成新的规则状态。

### 用户多 IP

目标为 `RelayUser`，统计窗口内去重后的客户端 IP 数量。

- 支持不同 IP 数量阈值；
- 支持最少请求数；
- 支持可信 IP 白名单；
- 支持恢复阈值，例如触发为不少于 4 个 IP，恢复为不多于 2 个 IP；
- IP 为空或被标记为未知时不计入不同 IP 数量，但会保留在事件样本中。

## 触发状态机

每条规则针对每个目标维护一条状态：

- `normal`：正常；
- `pending`：本次评估满足条件，尚未达到连续触发次数；
- `firing`：达到连续触发次数，事件已触发；
- `recovering`：已满足恢复条件，尚未达到连续恢复次数；
- `unknown`：数据不足、数据过期或适配器不支持。

首次触发时创建一个未恢复事件。事件在恢复前持续更新，不重复创建。达到连续恢复次数后补写恢复时间并关闭事件。

规则变更、规则停用或目标删除时，不删除历史事件；未恢复事件标记为规则停止或目标失效，并停止继续执行动作。

连续次数的默认值为触发 3 次、恢复 3 次。规则可以把触发次数设为 1，以支持低风险通知的快速响应。

采集失败与业务指标异常分开处理：采集失败先进入 `unknown`，连续采集失败达到配置次数后，才可由单独的“采集稳定性”规则生成预警。

## 自动化动作与恢复

动作执行必须幂等，并记录动作前后的状态。

触发动作：

- `disable_account_scheduling`：停止 `RelayAccount` 调度；
- `enable_account_scheduling`：恢复 `RelayAccount` 调度；
- `disable_user`：停用中转站用户；
- `enable_user`：启用中转站用户。

自动恢复保存以下信息：动作 ID、触发前状态、自动设置后的状态和执行时间。恢复时仅在以下条件同时满足时执行：

- 规则配置了自动恢复；
- 当前状态仍等于自动化动作设置后的状态；
- 目标没有被管理员手工修改；
- 恢复条件已经连续满足。

如果管理员在事件期间手工修改状态，系统记录人工介入，关闭自动恢复动作但保留恢复通知。规则选择“无自动恢复”时，同样只关闭事件和发送恢复通知，不修改目标状态。

动作失败不会阻止事件进入 `firing`，但会把动作状态标记为失败，并发送包含错误信息的通知。下一轮评估不会无限重复执行失败动作；只有动作重试策略允许时才重试，默认最多重试 3 次并使用递增间隔。

## 通知

现有通知渠道继续作为配置中心，预警中心通过规则关联选择通知渠道。Telegram、Webhook、邮件、企业微信、钉钉、飞书和 Bark 的配置与测试发送逻辑复用现有实现。

消息内容使用内置模板，模板根据事件类型填充：

- 规则名称和严重级别；
- 中转站、账号或用户；
- 触发指标、窗口、阈值和实际值；
- 连续触发次数和首次触发时间；
- 自动化动作及结果；
- 恢复时间和恢复原因。

规则允许配置短备注或前缀，但不开放整段正文编辑。这样可以保持所有预警消息结构一致，并为后续模板版本化保留空间。

通知冷却按规则 + 目标 + 通知渠道计算，默认 30 分钟。严重级别不同的事件不互相覆盖冷却记录。恢复通知不受触发通知冷却影响。

现有旧通知事件继续工作，旧的 `NotificationChannel.Subscriptions` 保留兼容；新增预警规则通过独立关联表选择通知渠道，不强迫已有配置迁移。

## 数据模型

新增模型：

### `alert_rules`

保存规则定义和稳定字段：目标类型、指标类型、名称、启用状态、严重级别、作用域、条件 JSON、动作 JSON、恢复 JSON、冷却时间和时间戳。

### `alert_rule_notification_channels`

保存规则与通知渠道的多对多关系，删除规则或通知渠道时级联清理关联，不删除通知发送历史。

### `alert_rule_states`

唯一键为规则 ID + 目标类型 + 中转站 ID + 目标外部 ID。保存状态、连续触发次数、连续恢复次数、首次异常时间、最近评估时间、最近有效样本时间、最后通知时间、自动动作信息和人工介入标记。

### `alert_events`

保存预警生命周期：规则、目标、严重级别、状态、触发值、阈值、样本摘要、触发时间、恢复时间、最后更新时间和去重键。去重键确保同一规则目标只有一个活动事件。

### `alert_action_logs`

保存事件关联动作、目标状态变化、执行结果、错误信息、重试次数和时间。

### `alert_metric_samples`

保存需要跨采集周期比较的标准化指标，例如账号倍率、余额、错误率、P95 延迟、窗口消耗和去重 IP 数量。用量金额和 IP 明细继续从 `RelayUsageEvent` 聚合，样本表保存评估结果和基线值，默认保留 30 天。

现有 `RelayUsageEvent` 增加稳定用户外部 ID和客户端 IP字段。已有记录没有外部 ID时使用邮箱回填兼容标识；没有 IP 的历史记录不会参与多 IP 规则。

## 后端模块与 API

新增 `internal/alert` 包，拆分为：

- `types.go`：规则、事件、状态和统一指标类型；
- `evaluator.go`：窗口、阈值、连续次数和状态机；
- `collector.go`：采集新鲜度判断和指标快照；
- `actions.go`：账号和用户动作及恢复保护；
- `service.go`：规则生命周期、评估编排和事件查询。

新增 API：

- `GET/POST /api/alerts/rules`：规则列表和创建；
- `GET/PUT/DELETE /api/alerts/rules/:id`：规则详情、更新和删除；
- `POST /api/alerts/rules/:id/test`：用当前快照测试规则，不执行动作；
- `GET /api/alerts/events`：按状态、目标、严重级别和时间范围查询事件；
- `GET /api/alerts/events/:id`：事件详情、样本和动作记录；
- `POST /api/alerts/events/:id/ack`：人工确认事件；
- `POST /api/alerts/events/:id/recover`：在无自动恢复时手工关闭事件；
- `GET /api/alerts/summary`：指标卡数据；
- `GET /api/alerts/settings` 与 `PUT /api/alerts/settings`：预警采集和评估设置。

现有 `/api/notifications/channels` 和 `/api/notifications/logs` 保留，通知渠道管理迁移到预警中心页面的“通知渠道”页签。旧的 `/notifications` 前端路径保留并指向新的预警中心页面，避免历史链接失效。

## 前端页面

预警中心沿用现有 GatewayOps 页面外壳，不修改全局导航样式。页面结构已经确认：

1. 第一行：页面标题和“新建规则”；
2. 第二行：待处理事件、运行中规则、通知渠道、自动化处置四个指标卡；
3. 第三行：方案 A 的四个页签，分别展示预警事件、订阅规则、通知渠道和发送记录。

规则编辑器按四步组织：

1. 选择目标类型和目标范围；
2. 选择指标、配置窗口、阈值和连续次数；
3. 配置自动化动作、恢复条件和冷却时间；
4. 选择通知渠道并预览内置消息。

事件详情展示命中样本、实际值、阈值、状态变化、动作日志、通知日志和恢复条件。适配器不支持的指标或动作在编辑器中禁用，并显示原因。

## sub2api 与 newapi 扩展

预警规则不直接依赖具体站点名称。中转站适配层提供统一能力和能力声明：

- 读取账号及用户；
- 读取账号倍率和请求用量；
- 读取请求状态、延迟、用户标识和客户端 IP；
- 修改账号调度状态；
- 修改用户状态。

适配器必须对不支持的能力返回明确的能力缺失错误。规则引擎遇到能力缺失时把目标标记为 `unknown` 或在规则编辑器中禁用，不使用默认值伪造结果。

sub2api 先接入当前已有的账号同步、用户用量、状态码、延迟和 IP 数据。newapi 后续只实现适配器接口并提供字段映射，规则评估、状态机、动作审计和通知都不需要改动。

## 错误处理与数据保留

- 单个中转站或账号采集失败不影响其他目标评估；
- 采集失败记录数据源、目标、错误和最后有效样本时间；
- 规则配置错误在保存时返回校验错误，后台评估不会执行无效规则；
- 动作失败写入动作日志并通知，不回滚已经成功的其他动作；
- 通知部分失败不影响事件和动作状态；
- 事件和动作日志默认保留 90 天；指标样本默认保留 30 天；
- 现有通知发送日志保留当前清理策略。

## 验证

后端测试覆盖：

- 固定阈值、相对变化和基线比较；
- 滑动窗口和最少样本数；
- `pending → firing → recovering → recovered` 状态转换；
- 触发与恢复滞回；
- 冷却和活动事件去重；
- 自动动作幂等、重试和人工介入保护；
- 账号与用户目标隔离；
- 采集失败、数据过期和适配器能力缺失；
- sub2api 适配器回归和 newapi 能力声明。

API 测试覆盖规则 CRUD、规则测试、事件筛选、事件详情、动作审计和权限中间件。前端测试覆盖规则编辑分步校验、目标类型切换、动作恢复条件、页签内容和不支持能力的禁用展示。

交付前运行后端 `go test ./...`、前端 TypeScript 检查、前端构建以及现有 UI 静态测试。
