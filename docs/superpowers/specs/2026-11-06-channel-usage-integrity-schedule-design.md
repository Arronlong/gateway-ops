# 全渠道用量核对与自动修复设计

**状态：** 已获用户确认，2026-11-06  
**目标：** 移除渠道页自动条数校对，增加可配置的全渠道每日用量对比与自动修复任务，同时保留单渠道手动操作。

## 验收标准

1. 渠道管理卡片不再自动请求或展示上游用量条数校对结果；现有单渠道“重新拉取历史”入口、范围选择、核对与修复报告及执行过程保持可用。
2. “系统设置 → 后台任务”新增“全渠道用量核对与修复”任务，可启用/停用、选择范围、设置每日执行时间，并显示任务历史。
3. 首次使用的默认设置为启用、每天北京时间 07:00、范围 24 小时。范围选项为“今天”“24 小时”“7 天”“All”。
4. 可在后台手动触发全渠道任务。手动和定时执行使用同一执行路径及当前保存的范围设置，并记录成功、失败、跳过渠道和执行日志。
5. 执行覆盖全部已配置渠道；单个渠道失败不阻断后续渠道。无法提供上游历史的手动余额渠道应明确记录为跳过，不调用不存在的历史接口。并发的全局执行应被阻止；已有单渠道锁继续防止同一渠道重叠操作。
6. “今天”按 `Asia/Shanghai` 的当天零点至执行时刻计算；“24 小时”和“7 天”是滚动时长；“All”从历史起点执行。结束时刻统一以本次任务开始时刻为基准；All 沿用既有安全截止策略（前移 2 分钟后按 5 分钟向下取整），在批次开始时计算一次并由所有渠道共享，避免长任务中窗口漂移。
7. 定时任务使用独立的 `Asia/Shanghai` 调度时区，不改变其他既有任务的时区行为。修改启用状态或时间后立即更新调度；关闭定时任务不关闭后台手动触发。
8. 设置沿用现有键值存储和后台任务记录，不要求数据库迁移。

## 实施方案

在 monitor 服务中新增全渠道编排方法，枚举渠道后逐个调用现有 `RefetchUsageHistoryWithReport`，复用既有的按渠道比较、修复、限流和进度报告逻辑。逐渠道捕获并记录错误，继续处理后续渠道；汇总总数、成功数、失败数和跳过数。后台定时器与手动接口均进入同一 scheduler 任务执行器，由现有任务运行记录保存历史。

新增的调度器独立使用 `Asia/Shanghai` 时区。时间和范围配置加入现有同步设置 API、存储默认值及前端类型；后台任务卡片提供启用开关、范围、`HH:mm` 时间控件、手动触发按钮和历史入口。保存配置后刷新该任务的 cron 项。全局运行使用原子运行标志，避免手动与定时任务并行执行。

渠道页删除仅用于自动条数校对的查询 hook、状态及错误展示；保留手动重拉弹窗和 SSE 流程。对已有 GET 校对 API 不做无关删除，避免扩大兼容变更范围。

## 验证

- 前端定向测试确认渠道页不再启用自动校对请求，且单渠道手动入口和提交仍存在。
- 后端单测覆盖四种范围边界、北京时间跨日、全部渠道遍历、手动余额渠道跳过、单渠道失败后继续、全局并发阻止和定时配置重载。
- API 测试覆盖新设置读写、非法范围/时间拒绝、手动触发及任务记录。
- 运行受影响的 Go 测试、前端定向测试、类型检查与生产构建。
- 代码验证完成后按仓库约定重启现有服务，并检查前端与后端健康状态。

## 文件范围预览

- `backend/internal/monitor/`：全渠道用量核对与修复编排及测试。
- `backend/internal/storage/model.go`、`backend/internal/storage/settings.go`：新增设置字段和默认值。
- `backend/internal/scheduler/`：每日北京时间调度、配置重载、手动执行共享入口与任务名。
- `backend/internal/api/`：设置读写扩展和该任务的手动触发路由。
- `frontend/lib/api-types.ts`、`frontend/lib/system-settings.ts`：设置类型及默认值。
- `frontend/app/system-settings-page.tsx`：后台任务配置和手动触发界面。
- `frontend/components/monitor/channel-usage-history.tsx`：移除自动校对展示，保留逐渠道手动流程。
- 上述模块对应的后端和前端定向测试文件。
