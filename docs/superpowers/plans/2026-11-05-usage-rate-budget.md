# New API 用量限流与连续历史核对

## 验收条件

- 每取得一页，立即对比并写入本地，然后才请求下一页。
- 按渠道账号持久保存「历史连续核对完成至」。最新数据和自定义区间正常，都不能跳过历史缺口。
- 例如连续完成到 10 月 20 日后被限流，则保留该边界和未完成页。重启后续查未完成页；需重建分页快照时从该边界继续。

## 源码依据

New API v0.9.0 的 `/api` 路由组套用 `GlobalAPIRateLimit`，以 `c.ClientIP()` 计数，超额返回 HTTP 429。默认 180 次 / 180 秒，可由 `GLOBAL_API_RATE_LIMIT` 和 `GLOBAL_API_RATE_LIMIT_DURATION` 修改。合租巴士实际版本和配置未确认。

对应源码：`common/init.go`、`middleware/rate-limit.go`、`router/api-router.go`。
上游：https://github.com/QuantumNous/new-api/tree/v0.9.0

## 实现

- 同一源站账号共享 60 次 / 180 秒滚动预算，至少间隔 2 秒。余额、倍率和用量共享。
- 429 后减半后续预算，遵守 Retry-After；无该响应头时冷却 3 分钟。403 不自动重试。
- 自动页面检查只查总数，不自动遍历月、周、天。手动全量和后台历史回补使用同一持久断点。
- 上游分页通常从新到旧。首页立即保存，但不推进连续边界；随后按末页到第 2 页核对，首页不会再取一次。
- 每页事务同时写入调用、本轮已见标识和未完成页。仅删除已完整覆盖时间段内的陈旧记录，不清空未读的数据。
- 边界不包含其对应时刻，防止同一时间戳跨页时跳过未完成记录。真实重复调用的序号也会跨页保留。
- 分页总数变化、页不完整或时序异常时，保存已收到数据，保留连续边界，下次从该边界重建分页。
- 后台每轮至多处理 3 页历史，下次继续。近期同步使用独立 ForwardSyncedAt，避开本轮历史覆盖范围。
- 指定时间范围保留分层定位，数据也按页写入，但不推进全量历史断点。
- SSE 每 10 秒保活，预算等待展示进度。页面按账号显示连续完成位置、已保存页数和调用条数；429 等待后可自动续查。

## 验证

定向测试覆盖每页先落库、限流后断点、重建任务续页、同时间戳跨页、事务回滚、分页变动及自定义区间隔离。使用 SQLite、httptest 和浏览器模拟接口验证，不主动向真实渠道发送测试拉取。

## 2026-11-06 修正历史保留的核对口径

本地完整历史可能多于上游现存日志。保留更早的本地记录后，不能又要求两边全部条数相等，否则正常完成的拉取也会永久报错。

- 持久保存 `HistoryAvailableSince`，记录上游当前可核对范围。它与 `HistoryVerifiedUntil` 分别表示范围下界和连续完成位置。
- 仅把可核对范围之外的更早本地数据计为 `retained_count`，它们继续保存和参与本地统计，不作为可修复差异。
- 旧版已完成断点缺少该范围时，只读取首尾页补充范围；收到的页仍立即写入，不回退或清空断点。
- 完成分页后仍有差异时，先刷新本轮上游汇总，避免拉取前的统计已过时。真正落在可核对范围内的差异继续分层定位并修复。
- 列表和重拉弹窗都使用相同的可核对口径，单独展示另保留的更早历史条数。
